# Implementation Outputs
## Purpose
This document specifies the expected deliverables upon completing a feature's implementation, making it ready for the Review phase.

## Principles
- **Complete Work**: Deliver fully functional, tested, and documented code.
- **Review Readiness**: Provide all necessary context for reviewers.

## Engineering Rules
- **Rule 1**: Produce committed, pushed code on a feature branch.
- **Rule 2**: Produce a completed Pull Request containing the Implementation Report Template.
- **Rule 3**: Produce passing automated checks (CI, linting, tests) on the PR.
- **Rule 4**: Produce visual documentation (screenshots/videos) attached to the PR.

## Best Practices
- Ensure the branch is up-to-date with the main branch before requesting review.
- Respond promptly to reviewer feedback.
- Keep the feature branch focused on the specific ticket to avoid scope creep.

## Common Mistakes
- ❌ Requesting review before CI checks have passed.
- ❌ Delivering code that doesn't fully meet the ticket's acceptance criteria.
- ❌ Failing to include visual documentation for UI changes.
- ❌ Including unrelated refactors in a feature PR.
