# Implementation Report Template
## Purpose
This document provides the standard structure for summarizing completed implementation work, typically used in Pull Request descriptions or release notes.

## Principles
- **Contextual Clarity**: Explain what was built and why.
- **Reviewer Guidance**: Highlight areas that need specific attention during review.
- **Visual Proof**: Provide screenshots or videos for UI changes.

## Engineering Rules
- **Rule 1**: The report/PR must include a summary of the completed features.
- **Rule 2**: The report/PR must link to the relevant issue tracker tickets.
- **Rule 3**: The report/PR must include "Before" and "After" screenshots or videos for UI changes.
- **Rule 4**: The report/PR must explicitly state any deviations from the original Engineering Plan.
- **Rule 5**: The report/PR must list any required deployment steps or environment variable changes.
- **Rule 6**: The report/PR must include instructions on how to test the changes locally.

## Best Practices
- Keep the summary concise but thorough.
- Use animated GIFs for complex interactions.
- If a technical compromise was made, explain the reasoning clearly.

## Common Mistakes
- ❌ Submitting a PR with an empty or vague description (e.g., "fixed bugs").
- ❌ Forgetting to include environment variable updates, causing deployment failures.
- ❌ Failing to provide testing instructions, slowing down the review process.
- ❌ Not explicitly calling out architectural deviations.
