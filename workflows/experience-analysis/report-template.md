# Experience Analysis Report Template
## Purpose
This document provides the standard structure for summarizing the findings of the experience analysis. It ensures the engineering team has a clear blueprint of the required interactions and states.

## Principles
- **Clarity**: clearly define the behavior for each interaction.
- **Actionability**: highlight areas requiring custom logic or specific libraries.
- **Comprehensive Coverage**: ensure all edge cases (errors, empty states) are documented.

## Engineering Rules
- **Rule 1**: The report must include an overview of the core user flows.
- **Rule 2**: The report must detail the strategy for page transitions and loading states.
- **Rule 3**: The report must list all custom animations and required technical approaches.
- **Rule 4**: The report must document the handling of empty, error, and success states.
- **Rule 5**: The report must summarize accessibility considerations (focus management, ARIA).
- **Rule 6**: The report must list any unresolved experience questions for the design team.

## Best Practices
- Use clear, descriptive language for animations (e.g., "fade-in upward over 300ms").
- Group interactions by page or by global component.
- Include links to specific design frames demonstrating the interactions.

## Common Mistakes
- ❌ Writing vague descriptions (e.g., "make it pop").
- ❌ Failing to specify animation timing and easing.
- ❌ Omitting the accessibility section.
- ❌ Not explicitly stating the required animation libraries.
